# Day41：为 Day22 变化制定专用复核波次

## 1. 今日介绍

### 为什么今天做这个

Day40 已经批准 Day22–Day28 作为正式复核范围，但七个节点不能随意排序。Day41 根据依赖图决定哪些节点必须先复核、哪些节点可以在同一阶段就绪。

### 和昨天的关系

Day40 释放的是“复核方案规划权限”。Day41 使用这项权限读取 Day30 依赖图，把获批范围拆成依赖安全波次；仍不修改 Day22，也不运行任何任务。

### 今天需要掌握的概念

1. 诱导子图；
2. 依赖就绪；
3. 同波独立；
4. 理论并行与实际并行的区别。

### 完成标准

七个节点恰好出现一次；Day22 独占第一波；所有范围内依赖边由早波指向晚波；每个节点保留 ZOS-API 或离线分类；没有任务获得执行许可。

## 2. 为什么不能简单按 Day 编号执行

Day 编号大体反映学习过程，但真正控制复核顺序的是证据依赖。例如 Day26 和 Day27 都依赖 Day22 与 Day25，它们彼此之间没有依赖，因此可以在 Day25 通过后同时进入“就绪”状态。

正确的问题不是“下一个编号是什么”，而是：

```text
这个节点引用的所有受影响上游是否已经复核通过？
```

## 3. 什么是诱导子图

完整 Day30 图包含 Day3–Day28。Day41 只关心正式范围 `[22, 23, 24, 25, 26, 27, 28]`，因此：

- 保留这七个节点；
- 只保留两端都在这七个节点中的依赖边；
- 范围外的上游证据视为当前已经可用。

这样得到的局部图称为本次复核范围的诱导子图。

## 4. 六个理论波次怎样得到

```text
Wave 1: Day22
Wave 2: Day23
Wave 3: Day24
Wave 4: Day25
Wave 5: Day26, Day27
Wave 6: Day28
```

解释如下：

- Day22 是变化源，必须先处理；
- Day23 直接引用 Day22；
- Day24 引用 Day23；
- Day25 同时引用 Day23 和 Day24，因此必须等 Day24；
- Day26、Day27 都要等待 Day25，但彼此无依赖；
- Day28 引用 Day27，所以处于最后一波。

## 5. 同一波不等于实际并行

Wave 5 中 Day26 和 Day27 可以同时“就绪”，但是否实际并行还取决于：

- 计算机资源；
- ZOS-API 许可证通道；
- 人工审查能力；
- 输出目录和文件是否会冲突。

Day41 不进行资源判断。后续任务会再把理论波次转换为资源可行的顺序槽。

## 6. 第一步怎样运行

在 VS Code 中打开：

```text
scripts/demos/day41_change_specific_review_wave_plan.py
```

点击右上角运行按钮，或在项目终端运行：

```powershell
python scripts/demos/day41_change_specific_review_wave_plan.py
```

## 7. 重点阅读哪些输出

- `nodes=7`：正式范围没有丢失节点；
- `affected edges=9`：范围内存在九条依赖边；
- `waves=6`：共六个依赖阶段；
- `max width=2`：最宽的波次包含两个节点；
- 每一行的 `execution released=False`：仍未批准执行。

## 8. 常见错误

- 把完整 Day3–Day28 全部纳入本次波次；
- 只按 Day 编号排序，不检查依赖边；
- 在 Day24 之前释放 Day25；
- 在 Day27 之前释放 Day28；
- 把同波节点直接解释为可以在当前电脑并行执行；
- 波次生成后自动开始运行任务。

## 9. 下一步

计划检查通过后，运行：

```powershell
python scripts/demos/day41_generate_change_specific_review_waves.py
```

该脚本生成 Day41 的 JSON、CSV 和 Markdown 波次报告。运行后重点确认：

- 六个波次与计划输出完全一致；
- 七个节点恰好出现一次；
- 范围内九条依赖边全部从早波指向晚波；
- 每个波次继续显示 `execution released=False`；
- Day22 和冻结证据的 SHA256 保持不变。

报告仍只是规划证据；下一步才会结合单通道 ZOS-API 和离线任务容量，制定实际资源槽。
