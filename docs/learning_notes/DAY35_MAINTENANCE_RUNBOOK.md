# Day35：项目维护运行手册

## 1. 今日介绍

### 为什么今天做这个

Day29-Day34 已经建立了六种维护能力，但如果它们彼此分散，下一次证据变化时仍然容易不知道从哪里开始。Day35 把这些能力封装成一条固定的维护路径。

### 和昨天的关系

Day34 的失败门是流程末端的安全保障。Day35 从 Day29 的登记入口开始，一直走到 Day34 的失败隔离和恢复条件。

### 今天需要掌握的概念

1. 运行手册；
2. 证据门；
3. 人工审批点；
4. 停止条件；
5. 恢复条件。

### 完成标准

Day29-Day34 六份报告的 SHA256 全部匹配，十个检查点覆盖变化登记、来源核验、影响范围、顺序、资源、审批与恢复，并且不自动运行任何科学任务。

## 2. 完整维护链

```text
变化进入
  ↓
Day29 登记定位
  ↓
指纹与来源核验
  ↓
Day30 依赖追踪
  ↓
Day31 影响定界 + 人工批准
  ↓
Day32 依赖波次
  ↓
Day33 资源顺序槽
  ↓
逐槽人工审批
  ↓
PASS：释放下一依赖槽
FAIL：Day34 隔离下游、保留无关分支
  ↓
修复上游证据 + 重新验证 + 人工恢复
```

## 3. 为什么手册不能自动重跑

“受到影响”只表示需要复核，不表示一定需要重新连接 Zemax。维护者需要先判断变化字段是否真的影响光学模型、分析配方或决策阈值，然后批准对应范围。

自动重跑会带来许可证占用、结果覆盖和无意义计算风险，所以 Day35 只生成手册与审计证据。

## 4. 十个检查点怎样理解

- CP01-CP02：先明确变化是什么、属于哪个实验；
- CP03：没有可信指纹，不解释旧报告；
- CP04-CP05：用依赖关系找到保守复核范围；
- CP06：由人批准范围，不由脚本擅自决定；
- CP07：上游先于下游；
- CP08：许可证和离线通道不超容量；
- CP09：每个槽结束后审核证据；
- CP10：失败时只锁定依赖分支，修复后才能恢复。

## 5. 恢复不是简单点击继续

BLOCKED 节点恢复前至少需要：

1. 找到 FAIL 节点的原因；
2. 修复或更新上游证据；
3. 重新验证其配置、输出与 SHA256；
4. 重新计算受影响范围；
5. 由维护者批准新的波次和资源槽。

## 6. 第一步运行

```powershell
python scripts/demos/day35_maintenance_runbook_plan.py
```

计划步骤只审计六份来源与十个检查点，不生成手册，也不执行科学任务。

## 7. 安全边界

- 不连接 ZOS-API；
- 不修改模型或已有结果；
- 不自动重跑；
- 不用节点数量形成隐藏完成度分数；
- 不把教学手册冒充工程批准；
- 不允许未经修复的 FAIL 下游直接恢复。

## 8. 第二步：生成维护手册

```powershell
python scripts/demos/day35_generate_maintenance_runbook.py
```

生成的 CSV 保存十个检查点，JSON 保存来源指纹和安全状态，Markdown 是实际可读的维护运行手册，流程图负责展示从变化进入到失败恢复的完整路径。
