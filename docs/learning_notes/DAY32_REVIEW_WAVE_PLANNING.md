# Day 32：依赖安全的复核波次规划

## 1. 今日介绍

### 为什么今天做这个

Day31 已经知道“哪些节点可能受影响”，但还没有说明应先检查谁、后检查谁。Day32 将复核集合按依赖关系拆成多个波次。

### 和昨天的关系

- Day30 提供完整依赖图。
- Day31 提供三个变化场景的保守复核集合。
- Day32 在每个复核集合内部重新检查依赖，生成可执行的先后层次。

### 今天需要掌握的概念

1. 诱导子图；
2. 依赖波次；
3. 理论并行与资源并行的区别；
4. 为什么同一波中的节点不能存在受影响依赖边。

### 完成标准

每个场景中的每个复核节点恰好出现一次，并且每条受影响依赖边都从较早波次指向较晚波次。

## 2. 什么是诱导子图

Day30 有 26 个节点，但 Day27 变化只影响 Day27 和 Day28。为这个场景排顺序时，没有必要把其他 24 个无关节点放进来。

只保留复核集合中的节点，以及这些节点之间原有的边，得到的图叫作当前复核集合的诱导子图。

## 3. 波次怎样形成

第一波只有变化源。完成一波后，检查剩余节点：如果某节点的所有“受影响上游”都已经完成，它就可以进入下一波。

例如：

```text
Wave 1: Day8
Wave 2: Day9, Day14
Wave 3: Day10, Day15
```

Day9 与 Day14 都依赖 Day8，但两者互不依赖，所以可以位于同一波。Day10 必须等 Day9，Day15 必须等 Day14。

## 4. 理论并行不等于真的同时运行

依赖图只说明“先后关系允许并行”，没有考虑：

- ZOS-API Standalone 许可证是否允许多个连接；
- CPU、内存和磁盘是否足够；
- 多个任务是否会写入同一文件；
- 是否需要人工审批后才能运行。

因此 Day32 只报告理论波次，不启动任何任务。资源约束将在后续单独处理。

## 5. 第一步运行方式

```powershell
python scripts/demos/day32_review_wave_plan.py
```

脚本会先打印“今日介绍”，再验证 Day31 和 Day30 的指纹，最后列出三个场景的每一波、ZOS-API 节点和离线节点。

## 6. 安全边界

- 不连接 ZOS-API；
- 不自动运行任何脚本；
- 不把波次宽度解释为计算速度；
- 不通过隐藏分数决定优先级；
- 不声称同波节点一定可以在当前电脑上同时执行。

## 7. 第二步：生成正式报告

```powershell
python scripts/demos/day32_generate_review_wave_plan.py
```

生成的 CSV 会把每个场景中的每个 Day 明确放进一个波次；JSON 保存机器可读的完整结构；Markdown 方便人工复核；图片负责直观展示波次和执行类型。
