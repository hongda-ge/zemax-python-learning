# Day33：资源可行的复核调度

## 1. 今日介绍

### 为什么今天做这个

Day32 的同一波次只表示任务之间没有未完成的受影响依赖。但实际执行还会受到许可证、CPU、内存和人工审批等资源限制。Day33 先加入一个简单、透明的教学资源模型。

### 和昨天的关系

- Day32：回答“依赖上什么时候可以开始”。
- Day33：回答“资源受限时应排到哪个顺序槽”。

Day33 不能让任务回到比 Day32 更早的波次，也不能省略任何任务。

### 今天需要掌握的概念

1. 资源容量；
2. 串行化；
3. 调度槽；
4. 依赖并行与资源并行的区别。

### 完成标准

每个场景中的任务恰好出现一次，波次顺序不倒退，每个槽最多有一个 ZOS-API 任务和两个离线任务。

## 2. 为什么要限制 ZOS-API 为单通道

这个项目此前已经遇到 Standalone 许可证和连接占用问题。因此教学计划采取保守假设：同一时刻只安排一个 ZOS-API 复核任务。

这不是在声称 Zemax 永远只能单连接，也不是电脑性能测试结果。它只是当前教学流程中容易审计、风险较低的调度边界。

## 3. 为什么离线任务容量设为两个

离线任务不连接 OpticStudio，通常只读取已有 JSON、CSV 并生成统计或决策报告。Day32 中同一波最多出现两个离线任务，所以教学模型允许一个槽放入两个离线任务。

这同样不是 CPU 基准测试。如果未来离线任务很重，仍需重新测量资源占用。

## 4. 一个拆分示例

Day32 中：

```text
Wave 2: Day9, Day14
```

两个都是 ZOS-API 任务。加入单通道限制后：

```text
Slot 2: Day9
Slot 3: Day14
```

它们的依赖层次没有改变，只是资源上不能放进同一个执行槽。

而下面这个波次可以保持在同一个槽：

```text
Wave 5: Day12, Day13, Day17
```

因为 Day17 使用一个 ZOS-API 通道，Day12 和 Day13 使用两个离线通道，三者没有超过声明的容量。

## 5. 调度槽不等于时间

Slot 1、Slot 2 只表示先后顺序。它们不表示每个槽都是一分钟、十分钟或一小时。没有真实运行时长数据时，不能生成可信的完成时间表。

## 6. 第一步运行

```powershell
python scripts/demos/day33_resource_schedule_plan.py
```

这一步只验证资源模型并打印调度计划，不运行任何 Day3-Day28 实验。

## 7. 安全边界

- 不连接 ZOS-API；
- 不运行复核任务；
- 不修改模型；
- 不估计任务耗时；
- 不把教学容量称为硬件基准；
- 不通过隐藏分数决定任务优先级。

## 8. 第二步：生成正式报告

```powershell
python scripts/demos/day33_generate_resource_schedule.py
```

生成结果包括任务级 CSV、完整 JSON、人工可读 Markdown 和资源槽图。图中的 `W2.1`、`W2.2` 表示同一个 Day32 波次被资源约束拆成两个子槽。
