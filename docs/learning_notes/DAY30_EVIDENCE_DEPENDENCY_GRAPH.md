# Day 30：实验依赖图与证据追溯

## 1. 今天要回答的问题

Day 29 建立了实验注册表，可以回答“某一天有哪些配置、脚本和笔记”。但一个可维护的实验编排系统还需要回答：

> 当前结论来自哪些上游实验？如果上游证据改变，哪些下游结论需要重新检查？

Day 30 将把 Day3—Day28 表示为有向无环图（DAG）。节点代表实验日，箭头由上游指向复用该证据的下游。

## 2. 两类箭头不能混淆

### 教学先修关系

例如 Day3 干运行之后才进入 Day4 真实连接。这表示学习和放行顺序，但不一定代表 Day4 直接读取 Day3 的结果文件。

### 科学证据依赖

例如 Day24 使用 Day23 的七点残余离焦指标进行验收。这里下游结论确实建立在上游报告或模型之上，上游变化可能使下游结论失效。

把两者分开，可以避免将“我先学了什么”和“结论实际依赖什么”混为一谈。

## 3. 为什么依赖图有价值

- 找到一个结论的证据来源，而不是只看最终数字。
- 判断上游模型或阈值改变后的重跑范围。
- 发现循环依赖，例如 A 依赖 B、B 又依赖 A。
- 识别复用最多的关键证据节点。
- 为未来的自动任务调度提供拓扑顺序。

## 4. 第一步运行方式

```powershell
python scripts/demos/day30_evidence_dependency_plan.py
```

第一步只会：

1. 读取最新的 Day29 实验总账；
2. 验证 26 个节点全部存在且没有文档缺口；
3. 检查依赖边唯一、方向向前且不存在环；
4. 检查 Day8 以后每条科学证据边都能在下游配置中找到对应的上游 Day 标记；
5. 打印拓扑顺序、最大输入依赖和最大输出影响。

它不会连接 ZOS-API，不会重新进行光学计算，也不会生成正式依赖图文件。

## 5. 需要理解的基础概念

- **节点（node）**：这里代表一天的教学实验。
- **边（edge）**：从上游证据指向使用它的下游实验。
- **入度（in-degree）**：一个节点依赖多少个上游节点。
- **出度（out-degree）**：一个节点影响多少个下游节点。
- **环（cycle）**：沿箭头能够回到原节点，会导致无法确定正确执行顺序。
- **拓扑顺序（topological order）**：满足所有上游先于下游的执行顺序。

## 6. 今天的边界

依赖图只描述已经人工审核的来源关系，不根据文件名猜测科学结论，也不通过“依赖越多越重要”之类的隐藏分数评价实验质量。Day29 是维护工具，因此不会被伪装成 Day3—Day28 科学证据链的一部分。
