# Day 31：证据变化影响传播与最小复核集合

## 1. 今天要回答的问题

Day30 已经把 Day3—Day28 表示为依赖图。Day31 使用这张图回答维护中非常实际的问题：

> 如果一个上游报告、模型或阈值发生变化，哪些后续实验可能受影响，应按什么顺序复核？

这称为 **Change Impact Analysis（变化影响分析）**。

## 2. 什么是传递影响

假设存在：

```text
Day A -> Day B -> Day C
```

Day A 改变不仅直接影响 Day B，也可能通过 Day B 间接影响 Day C。Day C 是 Day A 的传递下游节点。

Day31 的保守规则是：

```text
复核集合 = 发生变化的节点 + 全部可达下游节点
```

上游祖先和没有路径相连的旁支不会被加入集合。

## 3. 为什么叫“复核集合”而不是“自动重跑集合”

图只能告诉我们哪些结论可能受影响，不能仅凭一条箭头判断是否必须重新运行 Zemax：

- 有些节点需要重新进行 ZOS-API 光学计算；
- 有些节点只需重新读取上游结果并做离线计算；
- 有些变化可能经过人工判断后确认不影响某个下游字段。

因此 Day31 先按 `uses_zosapi` 和 `offline_only` 分类，但不自动执行任何脚本。

## 4. 三个教学变化场景

1. **Day8 基础证据变化**：观察靠近主干上游的变化怎样传播到大部分后续实验。
2. **Day22 误差预算变化**：观察中后段输入只影响机制与验收分支。
3. **Day27 包络报告变化**：观察接近末端的变化只影响很小范围。

这三个场景用于学习传播范围，不代表它们真实发生了变化。

## 5. 第一步运行方式

```powershell
python scripts/demos/day31_change_impact_plan.py
```

计划脚本会：

1. 校验 Day30 图和 Day29 注册表的 SHA256；
2. 从变化节点沿箭头寻找全部传递下游；
3. 排除祖先和不相关旁支；
4. 按 Day30 拓扑顺序排列复核集合；
5. 区分含 ZOS-API 的实验日与纯离线实验日。

本步骤不会连接 Zemax、复制模型、计算新指标或自动运行任何实验。

## 6. 需要掌握的概念

- **直接下游**：通过一条边到达的节点。
- **传递下游**：通过一条或多条边能够到达的所有节点。
- **祖先**：沿反方向能够到达当前节点的上游节点。
- **变化源**：本次假设发生变化的报告、模型或规则所属节点。
- **复核顺序**：确保所有上游先于下游检查的拓扑顺序。

## 7. 今天的边界

影响节点数量不是重要性分数；受影响也不等于结果一定改变。Day31 只给出保守复核范围，不替代对具体字段、代码差异和工程要求的判断。
