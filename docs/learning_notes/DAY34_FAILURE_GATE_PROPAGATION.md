# Day34：失败传播与人工审批门

## 1. 今日介绍

### 为什么今天做这个

Day33 解决了复核任务怎样按依赖和资源排列，但默认每项复核都能通过。真实维护中，模型指纹改变、指标无法复现或 ZOS-API 分析报错都可能导致复核失败。此时必须阻止下游继续使用不可信证据。

### 和昨天的关系

- Day33 提供“哪个任务在哪个资源槽”；
- Day30 提供“失败任务有哪些传递下游”；
- Day34 把两者结合，得到失败后的状态分区。

### 今天需要掌握的概念

1. 人工审批门；
2. 传递下游；
3. 分支隔离；
4. PASS、FAIL、BLOCKED、REVIEWABLE。

### 完成标准

失败节点的全部传递下游必须被锁定，同时与失败证据无关的任务不能因为“排在后面”而被错误锁定。

## 2. 四种状态

- `PASS`：在假想演练中，失败槽及以前已完成且未失败的任务；
- `FAIL`：触发审批门失败的任务；
- `BLOCKED`：依赖失败证据、因此不得继续的传递下游；
- `REVIEWABLE`：尚未执行，但不依赖失败证据，经过重新审批后仍可复核。

所有状态都属于离线演练。本脚本不会实际运行任务，所以 JSON 中的 `actually_executed` 始终为 `false`。

## 3. 为什么不能简单地“后面全部停止”

以 Day9 失败为例，Day10 和若干决策下游依赖 Day9，因此必须锁定。但 Day14 是从 Day8 的另一条分支出发，并不依赖 Day9。把 Day14 也永久锁定会扩大维护成本，这叫分支误伤。

所以 Day34 采用：

```text
失败节点及其传递下游 -> FAIL / BLOCKED
无依赖的未来节点       -> REVIEWABLE
```

`REVIEWABLE` 不代表自动继续，它仍需要人工重新审批。

## 4. 为什么审批门放在槽结束后

Day33 允许一个资源槽中同时出现一个 ZOS-API 任务和离线任务。Day34 教学模型假设槽内任务先全部结束，再统一检查结果。因此同槽中的无依赖兄弟任务可以记为假想 PASS。

如果未来需要“槽内一失败立即中断”，必须另外定义进程取消、临时文件清理和部分结果状态，不能偷偷混入当前规则。

## 5. 第一步运行

```powershell
python scripts/demos/day34_failure_gate_plan.py
```

这一步只打印四个失败演练，不创建真实错误、不连接 ZOS-API，也不修改任何历史结果。

## 6. 安全边界

- 所有失败均为假想状态；
- 不自动执行历史实验；
- 不把“排在失败之后”等同于“依赖失败”；
- 不采用全局一刀切停止；
- 不使用隐藏优先级分数；
- BLOCKED 和 REVIEWABLE 均未实际运行。

## 7. 第二步：生成正式报告

```powershell
python scripts/demos/day34_generate_failure_gate_report.py
```

生成的 CSV 为每个演练、每个 Day 保存一个明确状态；JSON 保存完整传播证据；Markdown 方便人工审核；图片按 Day33 槽位展示四种状态。
