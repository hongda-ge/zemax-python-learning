# Day42：变化专用的资源可行复核调度

## 1. 为什么今天做这一步

Day41 已经回答了“哪些任务在依赖关系上可以进入同一波”，但还没有考虑本机能够同时提供多少执行通道。

Day42 加入两个明确的教学容量：

- 每个调度槽最多安排 1 个 ZOS-API 任务；
- 每个调度槽最多安排 2 个离线任务。

今天只生成调度方案，不连接 Zemax、不修改 Day22，也不执行 Day22-Day28。

## 2. 和 Day41 的关系

Day41 是依赖层：

> 上游证据完成以后，哪个下游节点才具备复核条件？

Day42 是资源层：

> 已经具备复核条件的节点，在声明的资源容量下应放进哪个顺序槽？

资源调度不能改变 Day41 的科学依赖顺序，只能在同一波内部进行容量拆分。

## 3. 需要掌握的概念

### 3.1 资源容量

容量表示一个槽内最多可以容纳多少同类任务。这里的 `1` 和 `2` 是教学假设，不是对真实电脑性能或许可证能力的测速结论。

### 3.2 资源槽

Slot 只表示顺序组。例如 Slot 5 晚于 Slot 4，但不能据此推断每个槽需要一分钟、一小时或一天。

### 3.3 容量拆分

如果某个依赖波次有两个 ZOS-API 任务，而容量只有一个，就必须拆成两个子槽；这叫资源串行化，不代表它们之间新增了科学依赖。

### 3.4 人工释放

进入调度槽只代表“方案中安排到这里”。`execution released=False` 表示仍需后续人工审批，当前不能运行。

## 4. 本次预期结果

Day41 的 Wave 5 包含两个离线任务 Day26、Day27，刚好等于离线容量 2；其余波次每波只有一个任务。因此预期：

- 理论波次：6；
- 资源槽：6；
- 因容量限制新增的槽：0；
- 最大槽宽：2。

这不是“资源限制没有意义”，而是证明当前七节点方案本身已经满足声明容量。

## 5. 第一步运行方式

```powershell
python scripts/demos/day42_change_specific_resource_schedule_plan.py
```

该脚本只打印并验证计划，不生成输出目录。

## 6. 完成标准

- Day41 报告和 Day22 指纹保持一致；
- 七个节点恰好进入一个资源槽；
- 来源波次顺序不倒退；
- 每槽不超过 1 个 ZOS-API 和 2 个离线任务；
- 所有槽继续显示 `execution released=False`；
- 不产生运行时长、资源性能或自动执行结论。

## 7. 第二步：生成正式证据

PLAN ONLY 结果确认无误后，运行：

```powershell
python scripts/demos/day42_generate_change_specific_resource_schedule.py
```

该脚本会生成：

- 任务级 CSV：方便逐行检查每个 Day 所在的资源槽；
- JSON：供后续失败门和审批步骤读取；
- Markdown：供人工复核与项目归档。

生成报告仍不会连接 ZOS-API、修改 Day22 或执行任何复核任务。
