# Day48：执行获批的 Day22 隔离候选

## 1. 为什么今天才真正运行

Day45–Day47 分别完成候选准备、候选审核和执行审批。到 Day48，项目才同时具备：

- 明确的冻结候选；
- 可复核的双指纹；
- 单字段差异证据；
- 一次执行许可；
- 固定的入口、输出目录和停止条件。

这说明安全自动化不是“有脚本就运行”，而是先建立证据和权限边界。

## 2. 和 Day47 的关系

Day47 的审批记录规定：

- 只能执行 Slot 1 / Day22；
- 只能执行一次；
- 必须显式使用 `0.012 mm` 候选；
- 必须使用 Day48 专用入口；
- 输出必须隔离；
- 结束后停在 CP09；
- Slot 2-6 不得自动释放。

Day48 的任务是严格实现这个运行契约。

## 3. 为什么不能直接运行原 Day22 脚本

原 Day22 脚本内部固定读取：

```text
configs/day22_focus_position_error_budget.yaml
```

该正式配置仍是 `0.010 mm`。直接运行会重复旧实验，而不是评估候选。

Day48 专用入口显式加载候选文件，因此不会把正式配置误当成新输入。

## 4. 什么是内存输出覆盖

候选是冻结证据，不能为了改变输出目录而编辑它。Day48 会：

1. 读取候选；
2. 在内存中复制配置对象；
3. 只在内存副本中设置审批规定的输出根目录；
4. 将结果写入隔离目录；
5. 再次验证磁盘候选 SHA256 没变。

这样既复用了 Day22 计算函数，也保持候选文件不可变。

## 5. 一次执行许可如何防止重复使用

Day48 在执行前搜索批准输出根目录中的 `slot1_execution_result.json`。如果已经存在，说明审批已经被消费，脚本会拒绝再次运行。

这不是绝对的安全系统，但它展示了“审批应当有使用次数和消费状态”的基本思想。

## 6. 第一步：执行前 PLAN ONLY

```powershell
python scripts/demos/day48_approved_day22_candidate_execution_plan.py
```

该步骤验证审批、候选、正式配置和 Day21 上游证据，但不计算结果、不创建目录。

## 7. 完成标准

- Day47 审批指纹有效；
- 候选值为 `0.012 mm`；
- 正式配置、候选和 Day21 证据指纹有效；
- 此审批此前没有被消费；
- 专用入口执行一次离线预算；
- 输出只写入批准目录；
- 不连接 ZOS-API，不计算新的光学指标；
- 完成后 `CP09=PENDING`，Slot 2-6 仍锁定。

PLAN ONLY 结果确认后运行：

```powershell

```

执行后不要再次运行同一命令。下一步应审核 Slot 1 结果，而不是继续执行下游任务。
