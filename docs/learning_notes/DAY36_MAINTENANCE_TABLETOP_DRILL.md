# Day36：维护手册桌面推演

## 1. 今日介绍

### 为什么今天做这个

Day35 已经形成完整维护手册，但手册还需要通过具体场景检查是否容易理解、是否存在跳步、失败后是否真的能锁定下游。Day36 选择 Day22 误差预算变化做一次端到端桌面推演。

### 和昨天的关系

Day35 提供十个检查点；Day36 不修改规则，只把一个假想变化依次放进这些检查点。

### 今天需要掌握的概念

1. 桌面推演；
2. 正常路线；
3. 失败注入；
4. 模拟状态与真实结果的区别。

### 完成标准

正常和失败两条路线都覆盖 CP01-CP10；Day23 假想失败后，Day24-Day28 被正确锁定；所有状态均带 `SIMULATED_` 前缀。

## 2. 为什么选择 Day22

Day22 本身是离线误差预算，但其下游同时包含：

- Day23、Day25：需要 ZOS-API 的光学复核；
- Day24、Day26-Day28：离线验收和决策任务。

因此一个场景就能同时检查依赖、资源容量、人工审批和失败传播。

## 3. 正常路线

正常路线假想 CP01-CP10 全部通过，最终状态为 `SIMULATED_COMPLETE`。这只验证流程结构，不代表任何实验真的通过。

## 4. 失败路线

失败路线假想：

```text
Slot 1: Day22 -> simulated PASS
Slot 2: Day23 -> simulated FAIL
Slot 3-6: Day24-Day28 -> BLOCKED
CP10: SIMULATED_NOT_APPROVED
```

恢复前必须修复 Day23 上游或分析问题、重验指纹、重新计算影响范围并获得人工批准。

## 5. 为什么所有状态都必须写 SIMULATED

桌面推演不连接 Zemax，也不读取新的光学结果。如果只写 PASS 或 FAIL，后续人员可能误以为这些是实际测量。`SIMULATED_` 前缀就是证据边界。

## 6. 第一步运行

```powershell
python scripts/demos/day36_maintenance_tabletop_plan.py
```

这一步只验证推演计划，不创建报告、不运行历史实验。

## 7. 安全边界

- 不连接 ZOS-API；
- 不修改 Day22 或任何历史证据；
- 不把模拟状态写成真实结果；
- 不跳过 CP06、CP09、CP10 人工门；
- 不允许未经修复直接恢复 BLOCKED 节点；
- 不生成隐藏的流程准备度分数。

## 8. 第二步：生成正式推演报告

```powershell
python scripts/demos/day36_generate_tabletop_drill.py
```

生成的 CSV 包含两条路线共二十条检查点状态；JSON 同时保存检查点和实验节点状态；Markdown 解释正常与失败路线；图片对比两条检查点路线和 Day22-Day28 的失败传播。
