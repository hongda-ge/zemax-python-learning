# Day44：Slot 1 隔离候选准备审批

## 1. 为什么今天不能直接执行 Day22

Day43 已经完成失败门设计，但“规划完成”不等于“可以运行”。更关键的是，Day37 申请评估的新值是 `0.012 mm`，正式 Day22 配置仍保存旧值 `0.010 mm`，而原有 Day22 脚本固定读取正式配置路径。

如果此时直接运行原脚本，只会重复计算旧值，不能回答变化申请提出的问题。

因此 Day44 只批准下一项安全动作：准备隔离候选输入。

## 2. 和 Day43 的关系

Day43 证明失败后能够正确锁定下游，但它没有批准任何真实任务。

Day44 读取：

- Day43 的失败门报告；
- Day37 的原始变化申请；
- Day35 的 CP09 人工槽门；
- 未改变的正式 Day22 配置指纹。

审批必须同时绑定这些证据版本，避免批准错误的变化或错误的调度版本。

## 3. 最小权限原则

本次只释放：

- 在 `outputs` 中复制并准备 Day22 候选配置；
- 计算候选 SHA256；
- 生成执行前清单。

本次不释放：

- 覆盖正式 Day22 配置；
- 运行 Day22 离线复核；
- 连接 ZOS-API；
- 计算光学指标；
- 释放 Slot 2-6；
- 声称工程变化已经获批。

## 4. 为什么候选文件要放在 outputs

正式配置是维护基线，直接覆盖后会让旧证据与新配置混在一起。隔离候选放在 `outputs` 中，可以明确记录：

- 它从哪个正式配置复制而来；
- 只改变了哪个字段；
- 改变前后的数值；
- 候选文件自己的 SHA256；
- 如果后续不批准，可以直接停止使用候选，而不需要恢复正式配置。

## 5. 条件批准不等于执行批准

决策状态是：

```text
SLOT_01_APPROVED_FOR_ISOLATED_CANDIDATE_PREPARATION
```

其中关键词是 `PREPARATION`。候选准备完成以后，还需要检查候选差异和指纹，再由新的审批决定能否运行 Slot 1。

## 6. 第一步运行方式

```powershell
python scripts/demos/day44_slot1_candidate_preparation_approval_plan.py
```

该脚本只打印审批计划，不生成审批记录，也不创建候选文件。

## 7. 完成标准

- Day43、Day37、Day35 和 Day22 指纹有效；
- 只批准 Slot 1 / Day22 / 离线任务的候选准备；
- 候选必须只改变声明的 `0.010 -> 0.012 mm`；
- 正式 Day22 配置保持不变；
- Slot 1 执行和 Slot 2-6 继续锁定；
- 不连接 ZOS-API，不声称完成真实变化。

## 8. 第二步：生成正式审批记录

PLAN ONLY 结果确认后，运行：

```powershell
python scripts/demos/day44_generate_slot1_candidate_preparation_approval.py
```

该脚本只生成 JSON 和 Markdown 审批记录。它不会创建候选配置，也不会执行 Day22。

正式记录的作用是让下一步能够回答：“候选准备是否真的获得了授权，它的边界是什么？”而不是依赖聊天记录或口头约定。
