# Day43：变化专用的逐槽审批与失败传播

## 1. 为什么今天做这一步

Day42 已经把七个复核节点安排进六个资源槽，但调度表只描述“先后顺序”，没有回答：如果某个复核失败，后面的任务应该怎样处理？

Day43 用离线桌面推演建立失败门。今天出现的 PASS、FAIL、BLOCKED、REVIEWABLE 全是假想状态，不是历史实验结果。

## 2. 和 Day42 的关系

Day42 回答：

> 在声明的教学资源容量下，每个复核任务放在哪一个槽？

Day43 回答：

> 一个槽完成后怎样人工审批？某个节点失败时，哪些下游必须锁定，哪些独立分支还可以继续复核？

调度槽来自 Day42，失败传播范围来自 Day30 的科学依赖图。

## 3. 四种状态

- `PASS`：在假想失败门之前已经完成且未失败；
- `FAIL`：本次演练主动注入失败的节点；
- `BLOCKED`：依赖失败证据的传递下游，禁止继续；
- `REVIEWABLE`：尚未完成，但不依赖失败节点，仍可等待人工决定。

四种状态必须互斥，并且合起来覆盖全部七个节点。

## 4. 为什么“同槽”不等于“依赖”

Day26 和 Day27 同在 Slot 5，只是因为两者都在 Day25 之后就绪，而且离线容量可以容纳两个任务。

- Day26 是终端分支，不是 Day27 的上游；
- Day27 是 Day28 的上游。

因此：

- Day26 假想失败时，Day27 可以保持 PASS，Day28 保持 REVIEWABLE；
- Day27 假想失败时，Day26 可以保持 PASS，但 Day28 必须 BLOCKED。

如果简单采用“同槽一个失败，全槽及以后全部停止”，就会错误地扩大失败影响范围。

## 5. 四个教学演练

1. Day22 失败：全部 Day23-Day28 被锁定；
2. Day23 失败：Day22 已通过，Day24-Day28 被锁定；
3. Day26 失败：Day27 已通过，Day28 仍可复核；
4. Day27 失败：Day26 已通过，Day28 被锁定。

## 6. 第一步运行方式

```powershell
python scripts/demos/day43_change_specific_failure_gate_plan.py
```

该脚本只在内存中计算假想状态，不生成结果文件，也不运行真实任务。

## 7. 完成标准

- Day42、Day30 和 Day22 指纹保持一致；
- 四个演练均覆盖七个节点且状态不重叠；
- 所有失败节点的传递下游均为 BLOCKED；
- 不依赖失败节点的未来任务保持 REVIEWABLE；
- Day26、Day27 的同槽分支隔离正确；
- 所有状态明确标记为 SIMULATED；
- 不连接 ZOS-API、不修改源文件、不声称发生真实失败。

## 8. 第二步：生成正式推演证据

PLAN ONLY 结果确认后，运行：

```powershell
python scripts/demos/day43_generate_change_specific_failure_gates.py
```

该脚本会生成：

- CSV：4 个演练 × 7 个节点，共 28 行模拟状态；
- JSON：保存完整状态分区及冻结来源；
- Markdown：供人工阅读和维护归档。

报告生成不代表任何真实任务失败，也不会释放复核任务。
